# Threat model review: WSL2 (2026-11-04)

Reviewed by the assistant that wrote the code, so NFR-S2's independent review is still open. Nothing
here was run on real WSL2.

**New boundary:** Windows. A Windows program runs outside the sandbox and its network rules, so the
routes from a sandbox to Windows count as escapes. Recorded as T-28.

| Route | Control | Checked |
|---|---|---|
| Reading a Windows drive | Every sandbox hides the mounts in the mount table | Real sandbox, with a folder as the drive |
| Starting a Windows program | `/init` and `/run/WSL` hidden | Real sandbox, with a stand-in `/init`; interop itself not run |
| VM sockets | srt's filter; in the core's sandbox, the core's own filter (since 2026-11-05) | Real sandbox on Linux: blocked everywhere, including the core's sandbox |
| Windows reading Linux files | None possible; accepted | Not run |
| Windows reaching local ports | Client keys and sign-in links, as for local programs | Not run |

**Was open, fixed 2026-11-05 (I1):** a VM socket from the core. srt skips its whole seccomp helper
where Unix sockets are allowed (its own docs say so), and the core needs them. The core now
refuses `socket(AF_VSOCK)`, `io_uring_setup` and foreign-ABI calls with its own filter
(`sandbox/vmsock.py`). Under WSL2 it won't start without it.

**Shown in a real srt 0.0.81 sandbox** on Linux, a kernel with VM sockets:
- A sandbox set up like the core's opened one before the fix, and gets `EPERM` after.
- Unix sockets still work.

**The doctor** now probes a sandbox set up like the core's, and a test shows it reports the gap
when the filter is missing.

**Still not seen:** what a VM socket would reach on real WSL2. With the filter, that's no longer
reachable.
